# ORM Mapping Specification — HMS-6 (Appointment Management)

For the Implementation Execution Agent: SQLAlchemy model expectations mapped from
`database/schema.sql`. This is a specification, not code — no ORM classes are generated by the
Database phase.

## Entity → Model Mapping

| Table | SQLAlchemy Model | Notes |
|---|---|---|
| `patients` | `Patient` | Placeholder model — minimal fields (`id`, `full_name`, `created_at`). Expect this to be superseded by a real Patient module later. |
| `providers` | `Provider` | Placeholder model — minimal fields (`id`, `full_name`, `specialty`, `created_at`). |
| `appointments` | `Appointment` | Core model. |
| `appointment_status_history` | `AppointmentStatusHistory` | Append-only; do not expose an `update`/`delete` repository method for this model. |

## Relationships

- `Appointment.patient` → many-to-one → `Patient` (`patient_id`)
- `Appointment.provider` → many-to-one → `Provider` (`provider_id`)
- `Appointment.status_history` → one-to-many → `AppointmentStatusHistory`, ordered by
  `changed_at` ascending. Use `lazy="selectin"` or explicit query when history is needed; do not
  eager-load by default on list endpoints (FR-020 visibility queries should stay lean).

## Status Enum

Map the `status` column to a Python `enum.Enum` (`AppointmentStatus`) with members
`SCHEDULED`, `CONFIRMED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`, `NO_SHOW`, using SQLAlchemy's
`Enum` type or a plain `String` with application-side validation — either is acceptable, but the
**state machine transition rules live in the service layer**, not the model.

## Transaction Boundaries

- **Booking:** insert `Appointment` + insert one `AppointmentStatusHistory` row
  (`from_status=NULL, to_status=SCHEDULED`) in a single DB transaction. On
  `IntegrityError` from the `excl_appointments_no_overlap` constraint, the repository must catch
  it and the service layer must translate it to a domain-level "slot conflict" error (→ HTTP 409),
  not let it propagate as a generic 500.
- **Reschedule/Cancel:** update `Appointment.status`/`start_time`/`end_time` + insert one
  `AppointmentStatusHistory` row in the same transaction. Never write the history row without
  the corresponding appointment update committing, and vice versa.
- Use the repository as the only place issuing SQL for these tables — service layer calls
  repository methods, never raw sessions directly (per the design spec's layering).

## Repository Expectations

`AppointmentRepository` should expose (at minimum):
- `create(appointment) -> Appointment` (raises on slot conflict)
- `get_by_id(id) -> Appointment | None`
- `list_for_patient(patient_id, date_range, status_filter) -> list[Appointment]`
- `list_for_provider(provider_id, date_range, status_filter) -> list[Appointment]`
- `update_status(id, new_status, actor_id, reason) -> Appointment` (writes history atomically)
- `reschedule(id, new_start, new_end, actor_id) -> Appointment` (writes history atomically)

No repository method should perform a bare `UPDATE appointments SET status = ...` without also
writing to `appointment_status_history` in the same transaction — that would violate NFR-018.

## Non-Responsibilities (per Database Agent scope)

This spec does not implement `repository.py`, `service.py`, `router.py`, or FastAPI database
session wiring — those belong to the Implementation Execution Agent.
